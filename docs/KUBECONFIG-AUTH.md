# Подключение только через kubeconfig — 0.5.0

## Что меняется

Единственный способ Kubernetes-аутентификации — self-contained kubeconfig с токеном или клиентским сертификатом и закрытым ключом. Внешние провайдеры, callback и redirect удалены из действующего приложения. Учётная запись Workbench и Kubernetes identity независимы. Исходный kubeconfig, токен или ключ не следует присылать в чат, issue или лог.

Сценарий: **kubeconfig → context → личная авторизация → namespaces → выбранный preflight → сохранение**. Ручного metadata-only подключения без credentials больше нет.

### Поддерживаемые credentials

| Формат выбранного пользователя kubeconfig | Поддержка |
|---|---|
| `token` | Да, передача Bearer по проверенному HTTPS |
| `client-certificate-data` + `client-key-data` | Да, mTLS; проверка пары, срока и назначения сертификата |
| `exec` / `auth-provider` | Нет; команды и плагины не исполняются |
| Пути к token/cert/key/CA | Нет; приложение не читает файлы по загруженным путям |
| Basic auth, impersonation, proxy, insecure TLS | Нет |

Для kubeconfig, ссылающегося на локальные файлы, подготовьте self-contained экспорт самостоятельно в доверенной среде. Не включайте исполнение загруженных команд на сервере. Если файл требует внешнего login-плагина, наличие одного файла ещё не означает наличие готовых credentials.

Сертификат может быть административным, в том числе в k3s. Workbench не уменьшает Kubernetes RBAC импортированного пользователя. Предпочтительна отдельная read-only identity с необходимой областью доступа. Чекбоксы ограничивают действия приложения, но не меняют права в Kubernetes.

## Подключение

1. Administrator открывает мастер, импортирует kubeconfig и явно выбирает context.
2. Выбранный context должен содержать inline token или cert/key. Неподдерживаемый формат требует подготовки self-contained kubeconfig, без переключения на другой способ входа. Название и окружение остаются обычными metadata.
3. Выберите режим личного хранения. По умолчанию — на один запуск, не более часа и не дольше текущей web-сессии. Явное повторное использование — не более 24 часов. Срок сертификата может сократить этот интервал.
4. Создаётся личный черновик и зашифрованный credential выбранного пользователя. Весь YAML и credentials остальных contexts не сохраняются. Статус авторизации приложения сам по себе ещё не доказывает, что Kubernetes примет credentials: это проверяется запросами discovery/preflight.
5. Получите список namespaces и отметьте нужные. Начальный выбор пустой. Выполните preflight и сохраните. Готовое подключение содержит только явно выбранный allowlist.
6. Перед запуском выберите подмножество этого allowlist. `run_only` расходуется атомарно при постановке запуска в очередь, **не** при discovery/preflight. Worker использует неизменяемую зашифрованную копию credentials и scope.

### Сеть всё ещё настраивается отдельно

В «Настройки → Подключения» требуется разрешающее правило **Kubernetes**: точный host, порт, CIDR. Из kubeconfig автоматически не создаётся сетевой allowlist. Проверки CA/hostname/SNI, DNS pinning, запрет redirect/proxy сохраняются.

Если сеть ещё не разрешена, интерфейс сообщает о Kubernetes egress. Нельзя обходить это включением `insecure-skip-tls-verify` или широким разрешением всех адресов. Пустой deployment `egress_ceiling: []` остаётся deny-all, а не отсутствием ограничений.

## Namespaces: полный список, страницы и права

- При разрешённом `list namespaces` показываются возвращённые имена, включая системные. `namespace` из context — только подсказка, не фильтр списка.
- Один запрос discovery ограничен по времени, размеру ответа и числу страниц. Если имён больше 1000, «Загрузить ещё» продолжает snapshot следующими ограниченными порциями. До последней страницы список явно неполный.
- Continuation защищён и привязан к пользователю/сессии, кластеру, конкретным credentials и revisions. Он не может переадресовать запрос на другой endpoint. После истечения snapshot или замены credentials требуется обновить список.
- «Выбрать все загруженные» означает только уже показанные строки. Новые страницы не выбираются автоматически. В сохранённой области/одном запуске остаётся лимит **100 namespaces**; список просмотра не обрезается до100.
- При Kubernetes403 на listing приложение не может достоверно перечислить все namespaces. Доступен ручной ввод известных имён. Listing имён не доказывает доступ к workloads, поэтому выбранные namespaces проверяются отдельным GET-only preflight.
- Галочки не создают RoleBinding, не запрашивают Secrets и не дают дополнительных Kubernetes-прав. Рабочие отказы RBAC отражаются в покрытии, а не скрываются как успешный пустой результат.

## Хранение и повторная авторизация

Credentials принадлежат паре **пользователь–кластер**. Grant на подключение не передаёт другому пользователю чужой токен/ключ. Они хранятся через существующий purpose-bound encrypted Vault; API/worker остаются доверенной границей и имеют доступ к расшифровке.

Конечный срок личной авторизации Workbench — не гарантированный срок действия Kubernetes-токена. Opaque token может быть отозван раньше; непроверенный JWT не считается доказательством подлинности. Нет автоматического refresh или бесконечного lease.

После истечения/отзыва выберите повторный импорт kubeconfig для того же endpoint/CA/context. Новый импорт не меняет сервер или allowlist; старые личные авторизации/leases инвалидируются. Kubernetes401 не означает выход из web-сессии Workbench.

При mTLS Python/OpenSSL загружает cert/key через закрытые временные файлы, немедленно удаляемые после загрузки SSLContext, в том числе при ошибке. В Compose `/tmp` уже является tmpfs. Для самостоятельного развёртывания обеспечьте аналогичный memory-backed temporary directory; локальная dev-среда с обычным `/tmp` не даёт гарантии отсутствия кратковременного plaintext на диске. Не включайте эти файлы в backup и не передавайте ключи через argv/logs.

## Обновление существующей установки

**Изменения исходников не обновляют работающий Docker-образ.** Схема0.5.0 требует отдельной offline-миграции из0.1–0.4. Runtime и maintenance tags: `amberdata-workbench:0.5.0-local` и `amberdata-workbench-maintenance:0.5.0-local`. Revision: `0005_remove_oidc`.

Процедура предназначена оператору; не выполняйте её без подтверждённого окна обслуживания. Она относится только к этому проекту, не к соседнему Compose или production-кластеру.

1. Зафиксируйте исходную версию, Docker context и проект; сохраните старые runtime/maintenance images. Сохраните действующий master key отдельно от backup. Не генерируйте новый ключ.
2. Подготовьте новые образы, не меняя работающие сервисы. Убедитесь, что runtime и maintenance соответствуют одной версии исходников.
3. Остановите API и worker и остальные клиенты БД; PostgreSQL оставьте работать. Не используйте `down -v`, не удаляйте `.local`.
4. Через новый maintenance image выполните `python -m workbench.admin upgrade` без `--apply`: проверьте обнаруженную старую схему и preview.
5. Создайте offline backup по новому, не существующему имени: `python -m workbench.admin backup /backups/pre-kubeconfig-auth.dump --offline-confirmed`. Сохраните архив и manifest. Проверьте восстановление в **другую пустую выделенную БД** с действующим master key.
6. После проверки backup и остановки клиентов: `python -m workbench.admin upgrade --apply --backup-confirmed --offline-confirmed`.
7. Проверьте `python -m workbench.admin status`; запустите API и worker одной новой версии. Проверьте вход, существующие allowlists/историю и отсутствие удалённых настроек авторизации.
8. Повторно импортируйте личный kubeconfig в сохранённое подключение. Через штатную сессию выполните discovery и GET-only preflight сохранённого scope. Readiness приложения и успешный импорт сами по себе не доказывают доступ к Kubernetes.

Для команд maintenance используйте уже настроенные файлы secrets и mount backup-каталога, а не секреты в аргументах. Пример prefix: `docker --context desktop-linux compose -f compose.yaml -f compose.maintenance.yaml run --rm --no-deps maintenance`; после него — `upgrade`, `status`, `backup ...` согласно инструкции выше. UID/GID и каталог backup настройте как в [UPGRADE-B1.md](UPGRADE-B1.md).

Миграция сохраняет пользователей, grants, metadata, allowlists, находки и историю. Все подключения имеют тип kubeconfig, но миграция не создаёт identity и не превращает старые ID tokens в импортированные credentials. Все личные credentials и незавершённые authorization flows очищаются, queued work отменяется, running work прерывается, encrypted snapshots удаляются. После обновления нужен личный переимпорт. Это локальный отзыв использования, не отзыв токенов/сертификатов во внешней системе.

Старые схемы и миграции не переписываются. Offline backup/restore проверяет ciphertext прежних таблиц, если они присутствуют в старом архиве. Это совместимость восстановления, а не действующий внешний login.

### Откат

Destructive downgrade не используется. Остановите новую версию, сохраните её БД отдельно, восстановите проверенный pre-upgrade backup в **новую пустую БД**, верните прежние образы и тот же master key. Не запускайте старый бинарник на схеме0.5. Новые записи после backup не переносятся автоматически; их возможную потерю согласуйте заранее.

## Проверки и границы приёмки

Стандартные локальные проверки:

```sh
PYTHONPATH=src uv run --frozen pytest tests -q
bun run --cwd frontend test
bun run --cwd frontend typecheck
bun run --cwd frontend build
```

Изолированная PostgreSQL-проверка: `PYTHONPATH=src uv run --frozen python tests/smoke_namespace_postgres.py --maintenance-image amberdata-workbench-maintenance:0.5.0-local`. Текущий исходный код монтируется read-only. Скрипт создаёт собственные случайно именованные контейнеры с изолированной сетью и tmpfs-БД, без пользовательских volumes или published ports, проверяет upgrade/backup/restore и удаляет только свои контейнеры. Образы должны быть заранее доступны; ничего не скачивается.

[KUBECONFIG-VERIFICATION.md](KUBECONFIG-VERIFICATION.md) описывает историческую проверку0.4, не приёмку0.5. Unit/mocked integration tests не доказывают совместимость с конкретным k3s, Kubernetes RBAC или production-сетью. Live-проверка требует явного разрешения и выполняется отдельно от изолированных тестов. Обновление пользовательского Compose/БД — отдельная операция обслуживания.
