# Подключение и выбор namespaces — 0.3.0

> Историческая инструкция для 0.3. Начиная с0.4 OIDC необязателен: поддерживаются личные token/client certificate из kubeconfig и постраничное продолжение discovery. Актуальный сценарий и upgrade — [KUBECONFIG-AUTH.md](KUBECONFIG-AUTH.md). OIDC-only и предел1000 всего списка ниже относятся только к0.3.

Это изменение интерфейса, границ доступа и жизненного цикла подключения поверх B1. **B2-профили, живые Kubescape/Trivy и кластерные проверки не реализуются этим релизом.** Ниже описаны контракт и процедуры эксплуатации; результаты выполненных проверок публикуются отдельно в `NAMESPACE-VERIFICATION.md`.

## Порядок подключения

1. Импортировать kubeconfig и явно выбрать context **либо** ввести HTTPS endpoint/context/CA вручную.
2. Выбрать заранее настроенный OIDC-провайдер. Приложение создаёт личный черновик, не готовое подключение.
3. Пройти собственную Kubernetes OIDC-авторизацию. После callback мастер восстанавливается по id черновика. В URL нет токенов, в browser storage нет kubeconfig/credentials.
4. Явно получить список namespaces. Это отдельное чтение NamespaceList, без обследования workloads.
5. Отметить namespaces. По умолчанию список выбора пуст; namespace из context — только подсказка.
6. Проверить доступ к выбранным namespaced ресурсам и сохранить подключение. При частичном RBAC требуется подтверждение; ошибки подключения или аутентификации не являются частичным успехом.
7. Для каждого запуска отдельно выбрать подмножество сохранённой области. Ни новый namespace, ни refresh списка не расширяют область автоматически.

Исходный kubeconfig, токены, клиентские ключи, exec/auth-provider команды не сохраняются и не используются. Ручной режим не разрешает insecure TLS, произвольные команды или обход egress. CA Kubernetes и CA OIDC — разные настройки доверия. Авторизация остаётся персональной: grant подключения не передаёт чужой Kubernetes token.

### Черновики

Черновик видит только создавший администратор; срок жизни — 24 часа. Из него нельзя запускать проверки, импортировать отчёты или выдавать grants. Черновик можно возобновить или явно удалить. Просроченные черновики и связанное временное состояние очищаются; очистка не должна удалить подключение, которое одновременно стало готовым.

Метаданные endpoint/provider/context/CA черновика неизменяемы: для исправления создайте другой черновик. После сохранения проверенная личная авторизация остаётся действующей до истечения/отзыва/одноразового enqueue. Старые OIDC callbacks не могут восстановить прежнее состояние.

## Что означает выбор

- Поиск меняет только отображение; скрытые фильтром выбранные имена остаются выбранными.
- «Выбрать все» материализует текущий загруженный список. При фильтре отдельное действие выбирает только найденные по фильтру.
- Максимум — **100 namespaces в одной области**. Массовый выбор сверх лимита не обрезается молча.
- `kube-system`, `kube-public`, `kube-node-lease` помечены, но не скрыты и не выбраны автоматически.
- Refresh сохраняет выбранные имена; новые остаются неотмеченными. Имя, отсутствующее в свежем полном списке, показывается как требующее проверки, а не молча удаляется.
- Частичный список не используется как доказательство отсутствия namespace. Ограничение загрузки отображается явно.
- Ручной ввод валидируется как явные DNS labels. Wildcard, пустая область, URL/пути не допускаются.

У готового подключения есть административный allowlist. Запуск — только его подмножество, проверяемое backend. Worker использует сохранённый список, сопоставляет его с зашифрованным snapshot и текущей областью подключения, проверяет точный URL каждого чтения. Перед каждым запросом и сохранением результата повторяются проверки доступа. Уже отправленный синхронный GET может завершиться после отзыва, но новые запросы/публикация устаревшего результата запрещены.

Изменение allowlist администратором требует подтверждения пароля, актуальной revision и проверки выбранной области. При фактическом изменении прежние credentials/OIDC flows отзываются, queued jobs отменяются, active jobs останавливаются; неизменённая история запусков сохраняется. Новая область не переписывает прежние Run.scope.

## RBAC и ошибки

| Результат | Поведение |
|---|---|
| Полный NamespaceList | Показать имена как кандидатов, не как разрешённые проверки |
| NamespaceList 403 | Объяснить недостаток права перечисления, предложить ручной ввод |
| Kubernetes 401 | Требуется собственная OIDC-авторизация; web-сессия приложения не завершается |
| TLS/DNS/сеть/timeout/egress | Показать конкретную безопасную категорию; не возвращать ложный пустой список |
| Resource GET 403 в preflight | Показать конкретный пробел покрытия |
| Все probes недоступны | Не объявлять частичное успешное подключение |
| Неизвестный/malformed/неполный ответ | Ошибка либо явно неполный результат, не подтверждение доступа |

401 не доказывает именно истечение токена. 404 probe не доказывает отсутствие namespace. Успешный пустой namespaced LIST также не доказывает существование вручную введённого имени. Для ручного имени без discovery существование остаётся неподтверждённым; дополнительные права на Namespace GET ради этого не требуются.

### Необязательное право перечисления namespaces

Это **пример для рассмотрения администратором Kubernetes, не команда, выполненная приложением**. Он даёт только перечисление Namespace objects и не предоставляет чтение workloads. Binding к реальной identity нужно создавать отдельно по принятой процедуре доступа.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: amberdata-namespace-discovery
rules:
  - apiGroups: [""]
    resources: ["namespaces"]
    verbs: ["list"]
```

`cluster-admin` не нужен. Список Namespace objects может раскрывать имена организационных областей, поэтому право необязательно: namespaced Roles/RoleBindings и ручной ввод остаются рабочим вариантом.

### Preflight и покрытие

Текущий inventory содержит Deployments, StatefulSets, DaemonSets, Pods, Services, NetworkPolicies, Roles, RoleBindings, ServiceAccounts. Preflight выполняет только `GET ...?limit=1` для каждого **выбранного** namespace и вида. Это ограниченное чтение объектов для проверки `list`, а не сканирование безопасности и не постоянная гарантия доступа. Ответы workloads не сохраняются в preflight.

При финальном сохранении backend повторяет preflight. Подтверждение частичного покрытия допускает только явные resource-level 403 при наличии успешных probes. Authentication/TLS/network/policy/malformed/not_checked/unsupported ошибки не принимаются как успешное подключение.

Nodes, ClusterRoles, ClusterRoleBindings и остальные кластерные ресурсы **не обследуются**. Выбор всех namespaces не означает cluster-wide scan. Неподдерживаемые поля профиля/кластерного охвата отклоняются, а не игнорируются.

## API совместимость

- `POST /api/cluster-drafts` — нормализованные метаданные из kubeconfig или ручного ввода.
- `GET /api/cluster-drafts` и `GET/DELETE /api/cluster-drafts/{id}` — собственные черновики.
- `POST /api/clusters/{id}/authorize` — личная авторизация ready или собственного draft.
- `POST /api/clusters/{id}/namespaces/discover` — отдельное обнаружение.
- `POST /api/clusters/{id}/preflight` — выбранный subset для ready либо candidate scope собственного draft.
- `POST /api/cluster-drafts/{id}/finalize` — `{namespaces,expected_access_revision,accept_partial}`.
- `POST /api/clusters/{id}/scope/preflight` и `PATCH /api/clusters/{id}/scope` — административное редактирование области.

**Изменение поведения:** прежний `POST /api/clusters` с kubeconfig/context/namespaces сохраняется как устаревший адаптер создания **draft**, а не обход авторизации/preflight. Переданный список не становится разрешённой областью автоматически. Обновите интеграции на новый lifecycle. Существующие подключения после миграции остаются ready с прежним allowlist.

Локальные API-запросы требуют сессии и CSRF. Прямой Kubernetes 401 не пересылается как HTTP401 приложения; используется отдельный code/action. Namespace discovery не создаёт Run и не потребляет run-only credential. В Run.scope сохраняются явные namespaces, лимиты и `inventory_version: 1`; старая очередь несовместима с новым защищённым snapshot и завершается миграцией.

## Обновление существующей установки

Схема: `0.3.0`, Alembic head: `0003_namespace_selection`. Поддерживаются проверенные источники 0.1.0 и 0.2.0; старые frozen schemas не переписываются. Для 0.2 → 0.3 не выполняется повторное baseline stamp. Новая программа отказывается работать со старой схемой; старые API/worker нельзя оставлять одновременно с новой схемой.

**Процедура ниже предназначена оператору. В рамках разработки рабочее развёртывание не обновляется.** Используйте только этот проект, правильный локальный Docker context и выделенную БД. Не применяйте к соседнему `kubernetes-workbench/deploy`.

1. Зафиксируйте текущую версию и сохраните соответствующий старый runtime/maintenance image для отката. Сохраните внешний master key отдельно от backup. Не генерируйте новый.
2. Соберите runtime и maintenance 0.3.0 заранее, не перезапуская старые сервисы. Теги проекта: `amberdata-workbench:0.3.0-local` и `amberdata-workbench-maintenance:0.3.0-local`.
3. Запланируйте обслуживание: остановите **API и worker**, запретите их автоматические переподключения, закройте остальные клиенты. PostgreSQL оставьте работающим. Не используйте `down -v`, не удаляйте `.local`.
4. Запустите `python -m workbench.admin upgrade` через новый maintenance image: это preview. Он должен распознать точную исходную схему и показать план инвалидирования.
5. Создайте новый backup в защищённом каталоге, используя несуществующее имя: `python -m workbench.admin backup /backups/pre-namespaces.dump --offline-confirmed`. Сохраните archive **и** adjacent manifest, отдельно ключ. Выполните пробное восстановление в отдельную пустую БД.
6. Только после реальной проверки backup и остановки клиентов: `python -m workbench.admin upgrade --apply --backup-confirmed --offline-confirmed`.
7. Выполните `python -m workbench.admin status`, затем запустите API/worker **одной новой версии**. Проверьте вход, старые allowlists/историю, мастер черновика. Пользователи проходят Kubernetes OIDC заново.

Для Compose используйте prefix из актуальной конфигурации (пример для этого Mac):

```sh
docker --context desktop-linux compose -f compose.yaml -f compose.maintenance.yaml run --rm --no-deps maintenance upgrade
```

Остальные команды maintenance подставляются вместо `upgrade`; secrets читаются через штатные файлы, не через аргументы. Подробности прав backup-каталога, внешнего ключа и безопасного restore — в [UPGRADE-B1.md](UPGRADE-B1.md), но версии/пути перехода берите из этой инструкции.

Сохраняются users/password hashes, ready cluster metadata и allowlists, grants, findings/observations/история и уже настроенные B1 providers/policy. Удаляются старые credentials/OIDC flows, очищаются credential snapshots, queued jobs отменяются, running jobs прерываются. Это локальная инвалидизация, не отзыв JWT у IdP. Для исходной 0.1 действующая конфигурация по-прежнему переносится только явным legacy import; для 0.2 повторный import не нужен.

### Откат

Нет destructive downgrade. Остановите новую версию, сохраните её БД отдельно, восстановите **проверенный pre-upgrade backup в другую пустую выделенную БД** с прежним master key и запустите соответствующую прежнюю версию. Сначала проверьте restore/status и доступ к данным, затем переключайте сервис. Не запускайте прежний бинарник поверх схемы 0.3. Новые записи после backup при таком откате не переносятся автоматически — сохраните их отдельно и согласуйте потерю изменений.

## Ограничения приёмки

Отдельный opt-in smoke PostgreSQL: `PYTHONPATH=src uv run --frozen python tests/smoke_namespace_postgres.py`. Требует уже закэшированные `postgres:17.5-bookworm` и совместимый maintenance image (по умолчанию 0.2.0 как среда зависимостей с read-only mount **текущего** исходного кода; `--maintenance-image` меняет выбор). Создаёт только случайно именованные контейнеры с `network:none`, tmpfs-БД, без published ports, пользовательских volumes или `.local`; проверяет fresh/upgrade, backup/restore старой и новой схем, пропуск заблокированного черновика при очистке и совместимость identity-lock с FK-вставкой, затем удаляет только свои контейнеры по имени и метке. Ничего не скачивает и не заменяет рабочее развёртывание.

Локальные mocked tests не доказывают совместимость с конкретным Keycloak/Dex/Kubernetes, рабочую RBAC-модель, нагрузку или отказоустойчивость. Live приёмка выполняется отдельно на разрешённом тестовом стенде. Успех preflight не гарантирует доступ во время следующего запуска; фактические отказы отражаются в покрытии.
